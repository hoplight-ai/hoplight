## The five questions the brief asked

1. Can it be used to store an IP, a name or an email outside the contact field? Not an address by the route: the forwarder never reads the address into the body; it salts a daily hash with it and keeps nothing else (visitorHash). A name or an address a visitor types into a prop or a message is kept as typed: the scrub cuts email addresses and phone numbers only. Proof, row 9: a query prop sent as "mail tester@example.org, call (415) 555-0133 or +44 20 7946 0958, I am Jane Q Public at 10.0.0.7" was stored as "mail [email], call [phone] or [phone], I am Jane Q Public at 10.0.0.7". So: a visitor can put their own name in; the site never adds one.
2. Is the CORS allowlist exact? Yes. originPolicy matches the three external origins by exact string, then the site's own host. Live: Origin https://evil.example answered 403; a lookalike https://gut-check-hoplight.vercel.app.evil.example answered 403 on preflight; the real Gut Check origin got 204 with Access-Control-Allow-Origin echoing that one origin, methods POST and OPTIONS, headers Content-Type. A request with no Origin header (a script, not a browser page) is allowed as anonymous ingest; that is the design and it is bounded by the limits below.
3. Can the forwarder be made to hit any URL other than TOOL_SIGNAL_URL? No. The target is read from the environment in the route and nothing in the request reaches it.
4. Can the quick-tools route be reached without the Basic pair? No. It is on the middleware matcher and checks the pair itself (siteAuthCheck). Live: POST and GET /api/tool-signal answer 401 with a Basic challenge.
5. Does the table's row security leave anything readable with the anon key? No. Live catalogue read: row security on, zero policies, grants only to postgres and service_role. Live REST GET on tool_signals with the project's publishable key answered 401.

## Findings

### Medium: rows are unbounded by a rotating set of addresses

The limits are 120 events and 5 feedback notes per visitor per ten minutes, per running copy of the function and in memory (route.ts, `checkLimitIn`). They hold for one address (live: the sixth feedback in a minute answered 429 "slow down", and a seventh with a forged X-Forwarded-For header was still refused, so Vercel sets that header and a client cannot fake it). They do not hold across addresses or copies: a scripted sender with many addresses, or a burst that spreads over copies, can write without bound. Each row is small (props under 2 KB), but the table is on the live project with the business ledger, and a flood is a storage and egress cost and a mess in the reading.

Fix: a Vercel Firewall rate-limit rule on POST /api/signal (project hoplight), a few hundred requests an hour across all addresses; and a nightly trim that deletes event rows older than ninety days (feedback rows stay). Size: one rule, one scheduled statement. Owner: Whit for the rule; quick-tools for the trim.

### Low, fixed on sitesec1: a prop named ip or user agent was lost without a word

The store refuses any body with a prop named ip, ip_address, user_agent and so on (lib/tool-signal.mjs IDENTIFYING), by design. This route accepted such a prop, answered 202, forwarded it, and the store's 400 was only a server log. Proof: the first test feedback carried `props: {ip: ...}` with a message and a contact; it answered 202 and no row exists. A feedback note with it would vanish. On sitesec1 the same list is refused here with a 400 the sender sees (src/lib/signal.ts, tested in scripts/signal.test.mjs, "a prop that would name the visitor is refused here").

### Low: the visitor hash is reversible by whoever holds the salt

sha256(salt + UTC day + address), first 16 hex. With the salt and the table, the four billion IPv4 addresses are hashed in minutes on one GPU, so the hash is pseudonymous to Whit and anonymous to everyone else. That is the same recipe ai-election-errors uses and is fine as long as SIGNAL_HASH_SALT stays in Vercel's environment and out of every file. If it is unset, each running copy makes its own random salt (with a warning), hashes never match across copies and per-visitor counts are wrong; the six test rows share one hash, consistent with a set salt or one copy. Only Whit can see which.

### Low: free text is kept as the visitor typed it

Messages up to 2,000 characters and props up to 1,000 characters each are kept after the email and phone scrub. A `query` prop (Revenge or Justice sends the first 1,000 characters of the pasted text; Gut Check sends 500 characters of a typed take) can carry a name or a view. For the two children's apps this is the whole risk; see rumi-espanol-2026-11-07.md. Fix: each tool sends settings and ids, and where it sends typed text it says so under the box.

## Checked and clean

- Body cap 8 KB here (live: a 9 KB body answered 413) and 16 KB at the store; props 2 KB here, 4 KB at the store; message 2,000, contact 200; action 1 to 64 lower-case characters; path kept without its query or hash (row 9: "/portfolio?secret=1#frag" stored as "/portfolio"); unknown tool, underscore in an action, and a message on an event all answer 400 with a reason.
- What is never kept: the address, the user agent, cookies, the query string. The route reads only Origin, Host, x-forwarded-for (for the hash), Referer (path only), and Vercel's country and region headers.
- The store stamps its own time; the forwarder's `at` is dropped (storeBody).
- The forward runs after the answer is sent, with a 5 second timeout, so a slow store never slows a page; a failed forward is a warning, not an error to the visitor.
- The kit (public/kit/signal.js) sets no cookie and stores no id; it posts text/plain beacons so there is no preflight, and the route reads them as JSON; the Origin header is still sent, so the allowlist still applies.
- Migration 0044 is additive with a written rollback; the table's checks mirror the validator's limits.
